# Native graphics initialization and recovery

On 2026-11-20 the Fedora x86_64 runner presented the frozen desktop probe on both an Intel Iris Xe and Mesa llvmpipe. A private build of the same supervisor recovered from two kinds of post-frame device loss on X11 and Wayland. Fourteen scenarios reached their expected outcomes. The tests include two deliberate crashes and the stock application's missing-driver exit. RI-AC06 still requires the other native targets and review of the candidate integration. [Desktop acceptance](../rust-rewrite-plan.md#gui-acceptance-before-full-commitment) · [Native GUI](rw02-native-gui.md) · [Evidence checksums](../../tools/rust-qa/graphics/evidence/linux-x64.sha256)

## Executed cases

| Scenario | Desktop and adapter | Observed result |
| --- | --- | --- |
| Stock startup, two separate controls | X11, Intel or llvmpipe | Both drew a 114-colour sampled framebuffer and completed four successful Vulkan presents before Quit, exit 0. |
| Stock startup, unavailable driver | X11, deliberately missing ICD library | Zero maps and presents. The original supervisor returned its first-UI-pass error, exit 1. |
| Fallback during initialization | X11, only llvmpipe exposed | The preferred hardware selector returned an actual initialization error. Attempt two selected CPU, presented four times and exposed the localized status through AT-SPI. |
| All renderers unavailable | X11, missing ICD | Two attempts, zero maps and presents. StatusNotifierItem signalled `NeedsAttention` and advertised activation to retry. A new JPEG reached the inventory with the same worker. One explicit activation authorized two further attempts. Quit completed with exit 0. |
| Unhandled loss control | X11, llvmpipe | After a drawn frame and a keyboard edit the test destroyed the active logical device. wgpu delivered `Destroyed`. With the recovery guard disabled the original index-buffer staging operation panicked, exit 101. |
| Loss during a GUI frame, two cases | X11 and Wayland, llvmpipe | The callback and the original failing egui-wgpu staging path ran. A new surface displayed the retained draft. A subsequent key produced four successful presentations on X11 and three on Wayland. |
| Controlled driver loss during queue submit, two cases | X11 and Wayland, llvmpipe | wgpu delivered `Unknown` after receiving `VK_ERROR_DEVICE_LOST`. The bounded device drain reported `QueueEmpty`. The new editor took input and produced four additional presents on X11 and three on Wayland. |
| Intel-to-CPU fallback, two cases | X11 and Wayland, both real ICDs available | The supervisor released its private Iris Xe logical device and selected llvmpipe. X11 independently read 133 colours from the replacement window. Mutter committed buffers for the replacement titled toplevel. A new keystroke produced one XDamage event on X11 and two buffer commits on Wayland. |
| Second loss and user retry | X11, llvmpipe | Two consecutive `Destroyed` callbacks exhausted the automatic attempts. The worker processed the injected file while headless. Explicit activation created generation three with the retained draft. The item signalled `Active` and restored its normal title. |
| Unrelated application panic | X11, llvmpipe | The control produced its own assertion and exit 101. The device-loss callback and recovery counter both stayed clear. |

After each successful recovery from post-frame loss, AT-SPI read the previously edited `rw02`, the restored filename-field focus and the localized graphics notice. Sending a native `x` changed the field to `rw02x` and caused new drawing. The driver also checked the original child PID and kernel process start time, added a synthetic JPEG, observed directory access with inotify and waited for the same worker's new inventory result. It used the existing development inventory worker. The shipping synchronization engine is a later rewrite stage. ## Failure paths and integration

The shared supervisor at `6c953e32c0b2710bfe06b19805214946653480af` can detect initialization ending before its first UI pass. Once a frame has already drawn, a cumulative pass count cannot classify a renderer exit. The experiment records the device and a fresh generation for each renderer. Its wgpu callback atomically marks that generation lost and requests a redraw through a weak window reference. On the event-loop thread it exits the affected renderer, retains the supervisor, draft, semantic focus and worker, and builds a fresh surface. A late callback from a released generation has no effect. Recovery makes at most two attempts per episode. Only an explicit activation starts another episode after exhaustion. [Supervisor overlay](../../tools/rust-qa/graphics/supervisor.patch) · [Device state and adapter selection](../../tools/rust-qa/graphics/graphics.rs)

Calling the real `Device::destroy` between frames and during `Window::ui` exercises the wgpu `Destroyed` callback. For the in-frame case the pinned egui-wgpu 0.37.0 renderer panics when its index staging allocation fails. The experiment catches that single diagnostic at the eframe dispatch boundary only after the active device's loss callback. A different UI panic propagates. A fallible staging result in the pinned renderer would remove this dependence on diagnostic text. Adoption of a dependency patch or replacement archive requires its own source review. [Pinned index staging operation](https://github.com/emilk/egui/blob/7c0b40402271e8d40cda69f87cf3c2617c2e4382/crates/egui-wgpu/src/renderer.rs#L1033)

The independent software-driver case forwards a real `vkQueueSubmit` to llvmpipe. Once the private driver sees a successful return and consumes its one-shot marker, it returns `VK_ERROR_DEVICE_LOST` to wgpu for that call. This exercises the backend's driver-error branch with the original submission and fences still able to complete. In the first experiment wgpu delivered `Unknown` and subsequently panicked in `wgpu-hal 30.0.2` while tearing down a swapchain that still owned an acquired semaphore. The final supervisor calls `Device::poll` with a 500 ms timeout after confirmed loss before eframe releases the surface. Both measured driver-loss runs returned `Ok(QueueEmpty)` and reached a usable replacement. Permanent GPU hangs, timeout paths and physical GPU resets are outside this observation. The experiment leaves unexpected teardown panics visible. [One-shot Vulkan status observer](../../tools/rust-qa/graphics/submit_loss.rs) · [Locked graphics inputs](rw02-gui-dependencies.md)

The first mixed-adapter build also left focus on the replacement frame. The final build remembers which of the three controls held focus and reapplies that logical focus when its replacement window gains native focus. The probe sends no focus-navigation key after the loss. The private StatusNotifierItem exposes a title and emits `NewStatus` and `NewTitle` on entering or leaving headless failure. The test reads those properties and both signals on its private bus. Desktop-shell rendering of that indicator remains a separate observation. Keep the test-only destruction action, one-shot driver and raw control confined to QA when integrating this approach.

## Inputs and isolation

The builder applies a zero-context patch with zero fuzz to a source-hash-verified private copy of the frozen GUI. It runs Clippy with warnings denied and an offline Release build with the original Cargo graph, native toolchain, features and fonts. The base executable SHA-256 was `5bd230d24989fc251b789bb152afdf78e5a4353fda1150e809f6a250ef61af3f`. The private executable was `277c9a7021031f249d57a03ad22d51fb0610caf46278d1e3ae6d8d8ac0ceff3c`. The worker was `170a630b582ff3fc91716992632792c3dad7dc969aa84986617de0a60ed8aec4`. All 14 cases used the same driver files. Seven existing observation helpers came from local Git object `9e189bf06662a2286a1cbadd2efc14ac4a8e22e4`. Each run retained its sources, selected ICD manifest hashes, executable and observer bindings, process output and independent observations. [Private builder](../../tools/rust-qa/graphics/build.py) · [Input pins](../../tools/rust-qa/graphics/inputs.py)

Each run created new mount, PID, user, IPC and network namespaces, a private D-Bus session and a fresh synthetic home and media root. X11 used TigerVNC Xvnc 1.16.2. Wayland used Mutter 51.1 with a headless virtual monitor and the established Mesa Mailbox setting. The software runs had no DRM device. Hardware runs exposed a single DRM render node `226:128` and read-only PCI identification `8086:a7a0`. They presented through the real i915/Intel Vulkan stack into a private display. The personal desktop, its sockets, DRM primary node and monitor were outside the namespace. The Intel loss was limited to the application's logical device.

On X11 the observer sampled window pixels using `XGetImage` and counted XDamage. On Wayland it counted non-null buffer commits for the titled application surface and tracked each toplevel's life separately. Single-ICD cases also counted successful `vkQueuePresentKHR` returns. Two-ICD cases used the system Vulkan loader and external compositor evidence. The single-ICD observer rejects mixed dispatch tables. The host supplied Vulkan loader 1.4.350.0, Mesa 26.2.7 and GNU patch 2.8. All additional observation and build code stays in development tooling. ## Replay

Stage the native GUI, worker and original presentation observer using the performance guide. The graphics builder defaults to the retained `native-map-confirmed` subject. Pass `--base-subject` to select an equivalent source-bound native build on a second machine. Each build and measurement needs a new label. The following commands run from the repository root with the pinned offline inputs and the helper Git object available locally. [Build the baseline and worker](rw02-performance.md#replay)

```sh
python3 tools/rust-qa/graphics/build.py recovery-replay
subject=artifacts/rust/graphics/recovery-replay/subject
python3 tools/rust-qa/graphics/probe.py --name stock-replay --case stock --driver mesa
python3 tools/rust-qa/graphics/probe.py --name loss-replay --case driver-loss --driver mesa --subject "$subject"
python3 tools/rust-qa/graphics/probe.py --name paint-replay --case during-paint --driver mesa --backend wayland --subject "$subject"
python3 tools/rust-qa/graphics/probe.py --name exhausted-replay --case repeated-loss --driver mesa --subject "$subject"
python3 tools/rust-qa/graphics/probe.py --name unavailable-replay --case unavailable --driver absent --subject "$subject"
sha256sum --check tools/rust-qa/graphics/evidence/linux-x64.sha256
```

For the hardware cases use `--driver intel` with `--case stock` and `--driver intel-and-mesa` with `--case recover`. The launcher verifies the Intel render-only node before binding it. For the remaining cases use `--case init-fallback`, `--case raw-loss` or `--case unrelated-panic` with the private subject and `--driver mesa`. Each raw report names the exact arguments' case, backend and driver. The checked-in digest file identifies the original measured artifacts retained under `artifacts/rust/graphics`.

## Native coverage still required

Replay the software lane on native Linux ARM64 with the same reviewed inputs and ARM64 Vulkan loader and ICD. Record the actual adapter and each display's frame evidence. A hardware run requires an independently available render node and that device's reviewed loader configuration.

On native `windows-2025` x64 and `windows-11-arm` ARM64, extend the current synthetic GUI job's private control channel and UI thread event loop. Use a disposable interactive account and capture the actual DXGI adapter LUID, vendor/device ID, software flag, native architecture and FXC selection. The previous runs presented on the Microsoft Basic Render Driver. A separate isolated hardware-equipped runner is required for a hardware-to-WARP observation. [Existing Windows probe](../../tools/rust-qa/observe-windows-gui.py) · [Native runner matrix](../../.github/workflows/rust-desktop-assessment.yaml)

On each Windows architecture first establish a drawn HWND and an edited, focused UI Automation field. Exercise both logical `wgpu::Device::destroy` and a process-local DX12 removal on a disposable device. The pinned `windows 0.62.2` bindings expose `ID3D12Device5::RemoveDevice` and `ID3D12Device::GetDeviceRemovedReason`. Capture the HRESULT and callback, record the replacement adapter, then independently observe its HWND, actual DWM/DXGI presentation or captured frame, accessible status, restored focus, real input, live worker identity and new inventory. Repeat no-adapter, second-loss, explicit reactivation, ordinary Quit and unrelated-error controls. A physical reset or machine-wide TDR change is unnecessary. Application integration, timeout behaviour on other drivers and the four-target graphics gate remain open.
