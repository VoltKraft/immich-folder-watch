# Native graphics initialization and recovery

On 2026-11-20 the Fedora x86_64 runner presented the frozen desktop probe on both an Intel Iris Xe and Mesa llvmpipe. A private build of the same supervisor recovered from two kinds of post-frame device loss on X11 and Wayland. Fourteen scenarios reached their expected outcomes. The tests include two deliberate crashes and the stock application's missing-driver exit. The canonical integration and subsequent native runner findings appear below. RI-AC06 remains open. | Fallback during initialization | X11, only llvmpipe exposed | The preferred hardware selector returned an actual initialization error. Attempt two selected CPU, presented four times and exposed the localized status through AT-SPI. |

| Unhandled loss control | X11, llvmpipe | After a drawn frame and a keyboard edit the test destroyed the active logical device. wgpu delivered `Destroyed`. With the recovery guard disabled the original index-buffer staging operation panicked, exit 101. |

## Failure paths and integration

The shared supervisor at `6c953e32c0b2710bfe06b19805214946653480af` can detect initialization ending before its first UI pass. Once a frame has already drawn, a cumulative pass count cannot classify a renderer exit. The experiment records the device and a fresh generation for each renderer. Its wgpu callback atomically marks that generation lost and requests a redraw through a weak window reference. On the event-loop thread it exits the affected renderer, retains the supervisor, draft, semantic focus and worker, and builds a fresh surface. A late callback from a released generation has no effect. Recovery makes at most two attempts per episode. Only an explicit activation starts another episode after exhaustion. [Supervisor overlay](../../tools/rust-qa/graphics/supervisor.patch) · [Device state and adapter selection](../../tools/rust-qa/graphics/graphics.rs)

Calling the real `Device::destroy` between frames and during `Window::ui` exercises the wgpu `Destroyed` callback. For the in-frame case the pinned egui-wgpu 0.37.0 renderer panics when its index staging allocation fails. The experiment catches that single diagnostic at the eframe dispatch boundary only after the active device's loss callback. A different UI panic propagates. A fallible staging result in the pinned renderer would remove this dependence on diagnostic text. Adoption of a dependency patch or replacement archive requires its own source review. [Pinned index staging operation](https://github.com/emilk/egui/blob/7c0b40402271e8d40cda69f87cf3c2617c2e4382/crates/egui-wgpu/src/renderer.rs#L1033)

The original software-driver experiment forwards a real `vkQueueSubmit` to llvmpipe. Once the private driver sees a successful return and consumes its one-shot marker, it returns `VK_ERROR_DEVICE_LOST` to wgpu for that call. This exercises the backend's driver-error branch with the original submission and fences still able to complete. In the first experiment wgpu delivered `Unknown` and subsequently panicked in `wgpu-hal 30.0.2` while tearing down a swapchain that still owned an acquired semaphore. The final supervisor calls `Device::poll` with a 500 ms timeout after confirmed loss before eframe releases the surface. Both measured driver-loss runs returned `Ok(QueueEmpty)` and reached a usable replacement. Permanent GPU hangs, timeout paths and physical GPU resets are outside this observation. The experiment leaves unexpected teardown panics visible. [Original software-driver source](https://github.com/VoltKraft/immich-folder-watch/blob/27462474116603be88e476ed32a943b4fa1126c7/tools/rust-qa/graphics/submit_loss.rs) · [Locked graphics inputs](rw02-gui-dependencies.md)

The first mixed-adapter build also left focus on the replacement frame. The final build remembers which of the three controls held focus and reapplies that logical focus when its replacement window gains native focus. The probe sends no focus-navigation key after the loss. The private StatusNotifierItem exposes a title and emits `NewStatus` and `NewTitle` on entering or leaving headless failure. The test reads those properties and both signals on its private bus. Desktop-shell rendering of that indicator remains a separate observation. Keep the test-only destruction action, one-shot driver and raw control confined to QA when integrating this approach.

Stage the native GUI, worker and original presentation observer using the performance guide. The graphics builder defaults to the retained `native-map-confirmed` subject. Pass `--base-subject` to select an equivalent source-bound native build on a second machine. Each build and measurement needs a new label. The following commands run from the repository root with the pinned offline inputs and the helper Git object available locally. [Build the baseline and worker](rw02-performance.md#replay)

```sh
python3 tools/rust-qa/graphics/build.py recovery-replay

```

For the hardware cases use `--driver intel` with `--case stock` and `--driver intel-and-mesa` with `--case recover`. The launcher verifies the Intel render-only node before binding it. For the remaining cases use `--case init-fallback`, `--case raw-loss` or `--case unrelated-panic` with the private subject and `--driver mesa`. Each raw report names the exact arguments' case, backend and driver. The checked-in digest file identifies the original measured artifacts retained under `artifacts/rust/graphics`.

### Controlled submit on native Linux runners

At `8b071ab`, both Azure Linux jobs drew the native GUI on llvmpipe with LLVM 20.1.2. Both missing-driver controls passed including worker progress, native tray feedback, explicit retry and clean shutdown. The x64 Wayland run completed the original controlled submit case and recorded four successful Vulkan presents after the recovered editor accepted a key. The x64 X11 run and both ARM64 display runs terminated by SIGSEGV after wgpu's `Unknown` callback. None of those three reached the device-drain marker or a second renderer. The archives contain process output, window events and the accessible tree. They contain no crashing native stack. [x64 job 136631860365](https://github.com/VoltKraft/immich-folder-watch/actions/runs/44835826452/job/136631860365) · [ARM64 job 136631860438](https://github.com/VoltKraft/immich-folder-watch/actions/runs/44835826452/job/136631860438)

The old interposer let a healthy software driver accept real work and immediately changed the status to `VK_ERROR_DEVICE_LOST`. Vulkan permits the ICD to access submitted command buffers and semaphores until completion. wgpu could therefore start releasing resources while this particular test driver was still executing them. This timing explains a defect in the fault model. A crashing stack or a native rerun is needed to attribute an individual hosted signal to it. The integrated interposer now waits for the same externally synchronized queue to report `VK_SUCCESS` from `vkQueueWaitIdle` before reporting its one-shot error. It leaves the original submission, arguments and rendering intact. The isolated observer requires both successful Vulkan calls and the exact following callback order. A missing completion or callback fails the five-second observation. Ordinary resource runs use the system loader directly. [Scoped interposer](../../tools/rust-qa/graphics/submit_loss.rs) · [Vulkan submit lifetime](https://docs.vulkan.org/refpages/latest/refpages/source/vkQueueSubmit.html) · [Vulkan queue completion](https://docs.vulkan.org/refpages/latest/refpages/source/vkQueueWaitIdle.html)

Fedora x64 recorded the real queue idle after 2,223 µs on X11 and 1,454 µs on Wayland. Both runs then received `Unknown`, created generation two, restored the draft and focus, accepted the next native key, and processed a new file on the original worker. The key produced four and two additional successful Vulkan presents respectively. Independent in-frame `Device::destroy` runs on both desktops delivered `Destroyed` and also recovered the editor. The missing-ICD controls passed on both desktops. The integrated stage and fresh raw observations identify the exact interposer, GUI, worker and runner. The first hosted results above remain bound to the original interposer. [Native case assertions](../../tools/rust-qa/graphics/scenarios.py) · [Local artifact checksums](../../tools/rust-qa/graphics/evidence/integrated-linux-x64.sha256)

### Intel input on a virtual Mutter output

The private Fedora session exposed only its Intel render node and one 1280×900 Mutter virtual monitor. A GStreamer consumer received actual 4,608,000-byte BGRx frames from that monitor through private PipeWire and WirePlumber. The observer matched the monitor connector `Meta-0` to the Wayland output entered by the title-bearing surface. It timestamped every nonempty buffer and each injected key edge. The monitor produced frames on content changes. Its intervals describe recorded content during the experiment. [Monitor observer](../../tools/rust-qa/graphics/monitor_capture.py)

| Initial Intel presentation | Result | Distinct buffer timestamps | Frames during keyboard input | Median interval |
| --- | --- | ---: | ---: | ---: |
| Default, first complete capture | Intel-to-CPU recovery, new key and worker progress | 33 | 13 | 33.514 ms |
| Default, next capture | Last key missing from accessible text | 12 | 10 | 32.858 ms |

| Diagnostic Mailbox, same trace | Intel-to-CPU recovery, new key and worker progress | 33 | 15 | 33.298 ms |

In the traced default run the client requested `wl_surface#21.frame` at 23:16:56.343011 UTC. The Mesa queue attached a buffer, requested presentation feedback, issued FIFO barriers and committed. The server and client then recorded the final evdev key 3 press and release. Neither trace recorded completion of that outstanding frame callback before the timeout. The accessible filename retained focus. The private main thread's pre-debugger samples after the key showed `epoll_pwait`; the attached stack identified `polling::Poller`, calloop and winit's Wayland event loop. The client disabled its text input about 250 ms after the last frame request. The pinned winit 0.30.13 defers redraw delivery while a requested frame callback is pending. eframe 0.37.0 switches to a logic-only pass after 250 ms. Those paths are consistent with the observations. The trace does not establish why the private compositor ceased completing that surface's frames.
